# PlayerStatus imported baseline audit

Scope: read-only survey of the four Java classes, `plugin.yml`, `config.yml`, `pom.xml`, and the 17-section design transcript. Target is Paper 26.3 beta / Java 25 as specified by the product owner. No runtime test or build was run. **As shipped, the plugin does not complete a fresh enable**, so later behavior below describes the code paths if startup is repaired.

## 1. Blocking defects and high-severity behavior, ordered by severity

1. **Fresh-install enable fails.** `onEnable()` calls `loadStringPrefix()` and `loadStringNames()` (`src/main/java/com/gmail/crizardevelop/playerstatus/main.java:55-67`); the first `getString("tier-5.prefix").replace(...)` dereferences `null` (`main.java:164`). The bundled config defines only `tier-4` through `tier4` (`src/main/java/config.yml:1-36`), whereas the code also expects `tier-5` and `tier5` names and thresholds (`main.java:174,178,188,192,202`). Even if the prefix reads were guarded, absent thresholds read as zero and would misclassify status. This is a baseline configuration mismatch, independent of Paper version.
2. **PvP kills directly reduce social status, including consensual combat.** `PlayerDeathEvent` deducts one point whenever `getKiller()` exists (`src/main/java/com/gmail/crizardevelop/playerstatus/EventManager.java:24-29`), with no duel/arena check. This conflicts with design section 5's separation of Killing Psychosis and social status and the new duel requirement. `removeReputationPoint()` saves synchronously, then recalculates and saves the prefix again (`main.java:341-345,205-279`); the listener repeats that recalculation (`EventManager.java:28`).
3. **Reputation accounting is not trustworthy.** Votes use sender and target *names* as durable keys (`main.java:93-102,142-144`), but join initialization and `removeVoteForPlayer()` use UUIDs (`main.java:369-372,147-157`); that removal method cannot find normal votes. A name change can evade the one-vote check. Flipping bad to good adds only `+1` without reversing the previous `-1`, and flipping good to bad subtracts only `1` without reversing the previous `+1` (`main.java:108-135`); the stored tally then disagrees with the vote lists. No author/target/time/cost/reason event is recorded (`main.java:89-145`).
4. **Current execution blocks the server thread and persistence is unsafe for the planned product.** Every vote, admin edit, kill, first join, and tier update calls `saveConfig()` on the command/event path (`main.java:144,218-278,341-375`; `EventManager.java:18-29`). Paper documents that config file load/save I/O should be off-thread; whole-file YAML rewrites also grow with player/vote data. The separate score write, list write, and save are not atomic (`main.java:113-145`); a crash or failed save can leave them inconsistent. There is no error/transaction handling or audit log. Current handlers run on the server thread, so no current async race is shown; adding async chat, database, or scheduler work would create a thread-safety boundary around this mutable config and Bukkit `Player` access.
5. **The build and manifest do not target the decided platform.** Maven compiles for Java 8 and Spigot API `1.19-R0.1-SNAPSHOT` from the Spigot repository (`pom.xml:8-28`); the decided target is Java 25 and `io.papermc.paper:paper-api:26.3.build.135-beta`. The manifest still says `api-version: 1.21.5` (`src/main/java/plugin.yml:6`). This is an unsupported build baseline for reviewing 26.3 API compatibility, though Java 8 bytecode and a lower `api-version` are not, by themselves, proof of a load failure on Java 25/Paper. Paper remains compatible with Bukkit plugins; no currently imported Bukkit method was verified removed on 26.3. The Bungee `net.md_5.bungee.api.ChatColor` import (`main.java:8`) is legacy formatting, not a verified missing class.
6. **The tier ladder is internally inconsistent.** The negative tiers have positive `repRequired` values (`config.yml:1-16`), while `updatePlayerPrefix()` compares them as ascending negative ranges (`main.java:213-243`). With missing `tier-5` threshold defaulting to zero, neutral `0` and every negative score fall into tier `-5`; with a valid negative tier-5 threshold, the `30,20,10,1` order still makes several negative branches impossible. The neutral `rep0` is read but never used to select a tier (`main.java:197,243-249`). Prefix fields are static and cached once on enable (`main.java:16-50,65-67`), so YAML edits during play have no effect and there is no in-game editor.
7. **Commands can throw and can bypass policy.** The unconditional cast to `Player` crashes console use of every registered command (`src/main/java/com/gmail/crizardevelop/playerstatus/Commands.java:21-22`). `/pstatus info <offline-or-unknown>` passes a null target to `showStatusInfo()` (`Commands.java:45-51`; `main.java:387-392`). `/pstatus set` passes unchecked text to `Integer.parseInt()` (`Commands.java:76-84`). All target lookup is online-only (`Commands.java:47,78,92`), despite persistent social profiles. Admin add/remove/set modify scores without audit (`Commands.java:55-84`; `main.java:341-359`). `pstatus.evaluate` is checked but not declared in `plugin.yml` (`Commands.java:27-29`; `src/main/java/plugin.yml:18-36`), while `/utils` is declared/registered but has no handler (`plugin.yml:15-17`; `main.java:79-83`; `Commands.java:125`).
8. **An evaluation command can repeatedly mint or remove money.** `/pstatus evaluate` scans all online players (`Commands.java:25-30`); `isBadPlayer()` dispatches `eco take`/`eco give` on each call (`main.java:436-499`). The referenced `commandWhenPlayerIsEvaluated` values are absent from the bundled config (`config.yml:1-53`), yielding zero. There is no provider check, transaction result, idempotency, or meaningful time window; the “week” message labels do not correspond to weekly aggregation (`main.java:397-434`). With zero players, `evaluateAllPlayers()` reaches `substring(0, -2)` (`main.java:425-432`). These economy rewards/penalties also conflict with the design's payment-for-opinion economy and its soft social consequences.
9. **Some preconfigured content is unreachable or malformed.** The death command listener is commented out (`EventManager.java:32-35`). Were it enabled, `checkDeathAndReputationPlayer()` asks `getString()` for YAML lists and then parses their textual form (`main.java:501-523`; `config.yml:44-53`), so the config shape and reader disagree; it also calls the punitive `isBadPlayer()` as a side effect (`main.java:503`). `PrefixManager` has no active methods: its entire proposed body is commented out, although it still extends `JavaPlugin` (`src/main/java/com/gmail/crizardevelop/playerstatus/PrefixManager.java:7-9,208-209`).
10. **Resource location and naming need precise treatment.** `plugin.yml` and `config.yml` live under `src/main/java` (`src/main/java/plugin.yml:1`; `src/main/java/config.yml:1`) rather than the normal resources directory, but Maven explicitly includes both in the JAR (`pom.xml:31-41`), so location alone is **not** a demonstrated Maven packaging failure. It is fragile if another build path ignores that special block. `onEnable()` relies on `getConfig()` defaults and `saveConfig()` rather than explicitly copying defaults (`main.java:59-63`); missing keys and user-edited config are not validated. The lowercase `main` class matches the manifest exactly (`main.java:14`; `plugin.yml:3`), so capitalization is a maintainability issue, **not** a Java or Paper entrypoint blocker. The extra `PrefixManager extends JavaPlugin` is unused and should not become a second plugin entrypoint.

### Platform evidence

Paper's [project setup](https://docs.papermc.io/paper/dev/project-setup/) documents Paper API coordinates, repository and Java 25 toolchain; [getting started](https://docs.papermc.io/paper/getting-started/) states Java 25 for 26.1+. Paper's [plugin manifest](https://docs.papermc.io/paper/dev/plugin-yml/) and [configuration](https://docs.papermc.io/paper/dev/plugin-configurations/) guides show resource placement and warn about blocking file I/O. Paper's [chat event guide](https://docs.papermc.io/paper/dev/chat-events/) states that `AsyncChatEvent` is async and Bukkit API access there is unsafe. The owner-specified 26.3 build number is treated as an input to this audit, not independently asserted as the current latest build.

## 4. Architecture risks to resolve in the specification

- **Data model and identity:** The score is the only authoritative value, while vote lists are keyed by mutable names (`main.java:93-145,362-373`); there is no way to reconstruct provenance, adjust for decay, correct reversals, or distinguish Confidence/Psychosis. Target-wide honor limits and duels require explicit identities and lifecycles. An existing YAML file may contain inconsistent score/list history, so migration and trust in imported values are open decisions.
- **Persistence and economy consistency:** `config.yml` mixes defaults, live profiles, and votes, and rewrites all of it on the main thread (`main.java:59-63,142-144,341-375`). The design requires an auditable event and economic transaction together (`docs/reference/playerstatus-sistema-reputacion.md:194-204,319-333`); Vault's [Economy API](https://github.com/MilkBowl/VaultAPI/blob/master/src/main/java/net/milkbowl/vault/economy/Economy.java) returns a transaction response, but it does not make the plugin's own persistence atomic. The current console `eco` dispatch has no success result (`main.java:440-495`), no declared economy dependency (`pom.xml:21-29`; `plugin.yml:1-36`), and may repeatedly reward or penalize.
- **LuckPerms and configurable nodes:** Current `sender.hasPermission("pstatus... ")` uses Bukkit permission checks (`Commands.java:28,38,49,57,67,80,95,111`), which can be backed by LuckPerms for online players. No direct LuckPerms API is inherently required for those checks. The *node strings*, defaults and admin permissions are hardcoded or missing (`plugin.yml:18-36`), so the owner's YAML **and in-game** editing requirement needs a defined mapping/registration behavior; changes must remain compatible with LuckPerms grants. The undeclared `pstatus.evaluate` node is a concrete mismatch.
- **Paper scheduler and thread ownership:** Current event/command work is synchronous (`Commands.java:21-125`; `EventManager.java:18-35`). Cosmetic despawn and rate limits need scheduled timing; file/database I/O needs an off-thread path; entity, player and inventory changes belong on the server thread. Paper's [scheduler guide](https://docs.papermc.io/paper/dev/scheduler/) warns that much Bukkit world API is unsafe asynchronously. `AsyncChatEvent` is async, so mutable profile/config access needs a safe snapshot or handoff ([Paper chat events](https://docs.papermc.io/paper/dev/chat-events/)).
- **Adventure, MiniMessage and `&` input:** Current text is concatenated with Bungee `ChatColor` and prefixes are converted by raw `&`→`§` replacement (`main.java:8,52,107-136,164-188,378-395`), which does not validate code sequences or support the design's near-black `#202020`, hover, or per-message gradient. Paper's [Adventure legacy serializer](https://docs.papermc.io/adventure/serializer/legacy/) supports `&` input and RGB formats, while rich hover/chat rendering requires Components. Configured and in-game text should have a single defined interpretation; treating user-provided strings as MiniMessage as well as legacy codes would be ambiguous ([Adventure FAQ](https://docs.papermc.io/adventure/faq/)).
- **GUI/inventory:** None exists (`Commands.java:21-125`). The design requires target, exact cost, reason and final confirmation before a charge (`docs/reference/playerstatus-sistema-reputacion.md:172-206`). Inventory clicks, double clicks, closes, relogs, stale balances, and target disconnects can invalidate that preview; permission and balance must be checked again before committing. This is a design risk, not a currently failing GUI implementation.
- **Prefix coexistence:** `setDisplayName`, `setPlayerListName` and `setCustomName` overwrite values on join and every score change (`main.java:205-208,281-338`), potentially clobbering other plugins' display names. No chat listener applies message colors; chat appearance depends on the server's chat formatter. `setCustomName` by itself does not establish visibility (`main.java:284-337`).

## 5. Open conflicts and questions for specification

1. **Honor price is unresolved.** Design §6 specifies `max(minimum, current actor balance × percentage)`, initially **0.50% for Trust and 0.75% for Distrust**, optionally escalating within a time window (`docs/reference/playerstatus-sistema-reputacion.md:137-156`). The owner additionally asks for a **fixed amount configurable in YAML** and says **“10% per honor”**; current votes are free (`main.java:104-145`). Decide whether “10%” means balance percentage, 10% of the fixed amount, a per-honor increment, or something else; whether positive and negative prices differ; and whether a minimum/progressive multiplier survives. No formula is selected by this audit.
2. **Meaning of “giving or removing honor” and cap.** Does “removing” mean Distrust (`−1`), undoing a prior positive honor, or both? Is `+3/−3` a cap on the target's aggregate score, on honors from each actor, or on distinct active endorsements received by a target? Are positive and negative counts separate and lifetime or resettable? What happens when a vote changes sign or an admin adjusts a score? The current per-sender sign lists answer none of this (`main.java:93-145`).
3. **PvP behavior conflicts.** The design says kills raise a separate Psychosis measure and should not automatically lower social status (`docs/reference/playerstatus-sistema-reputacion.md:125-135`); the owner explicitly exempts consensual duel kills from *status* loss; the baseline deducts on every credited player kill (`EventManager.java:24-29`). Decide whether non-duel kills ever change social status, whether duel kills count toward Psychosis, and how arenas/events, environmental deaths with credited killers, and group duels are classified.
4. **Harassment effects versus social-only consequences.** The design forbids combat buffs and serious gameplay impairment (`docs/reference/playerstatus-sistema-reputacion.md:49-75,88-111`). Speed III silverfish are only consistent if they cannot attack, push, persist, drop loot/XP, or interfere with combat; sounds/messages need bounds and opt-out/accessibility rules. The near-black rare messages differ from the design's darkening of the player's own chat *messages* (design §3). Are they ambient private messages, public chat injections, or both? Should fake join/leave be visible to the target only, nearby players, or globally? They could be confused with real server events.
5. **Economy effects conflict.** Design §6 charges the **actor** for an opinion; the baseline's evaluation command rewards or fines the **target** repeatedly (`main.java:397-499`). Are evaluation payouts/sanctions to be dropped, retained under separate rules, or translated into social cues? The bundled `defaultCodes.deathPlayer` grants items by reputation (`config.yml:44-53`), another potential material benefit contradicting design §1/§11; its handler is currently inactive (`EventManager.java:32-35`).
6. **Tier scale and visual identity need explicit bounds.** The owner says preserve the current nine Spanish named `[|]` prefixes (`config.yml:1-36`); `main` expects eleven tiers including undefined `±5` (`main.java:16-50,163-203`). Negative `repRequired` values are positive (`config.yml:1-16`). Specify score range, signed boundaries, whether visual tiers are exactly nine, and where neutral/new players fall. Preserve the visual tokens/colors while fixing storage and resolution.
7. **Configurable strings versus manifest permissions.** The owner requires every node, message, and plugin chat prefix/color editable from YAML and in-game. Current permission checks and many messages are literals (`Commands.java:28-111`; `main.java:107-136,378-395,440-494`), while manifest nodes/defaults are static (`plugin.yml:18-36`) and `pstatus.evaluate` is undeclared. Decide which node identifiers may change live, how registration/defaults migrate, who may edit them, and how existing LuckPerms grants are handled. Clarify whether “plugin chat prefix” means the `Reputación ·` notification prefix (`main.java:52`) as well as each tier prefix and chat name display.
8. **Command surface and access.** The design proposes `/status ...` with trust/distrust/comments/vouch/psychosis/admin (`docs/reference/playerstatus-sistema-reputacion.md:335-346`); baseline has `/pstatus`, `/reputation`, and unused `/utils` (`plugin.yml:8-17`; `Commands.java:24-125`). Decide aliases, console/admin support, offline target support, and how player name changes appear. Existing direct admin score edits have no audit (`Commands.java:55-84`), conflicting with design §15/§17.
9. **Reputation reversibility, decay and historical data.** Design §§7 and 14 require a durable author/time/cost/reason event and possibly decay (`docs/reference/playerstatus-sistema-reputacion.md:158-170,319-333`); the baseline stores an integer plus mutable name lists (`main.java:93-145,362-373`). Decide whether to import that score as unverified legacy state, migrate votes, or reset. There is no reliable way to infer historical costs, comments or actors after name changes.
10. **Confidence thresholds and “unique users.”** The design calls for Unknown/Low/Established/High based on unique participants and diverse interactions (`docs/reference/playerstatus-sistema-reputacion.md:113-123`), but gives no numeric thresholds, age weighting, alt-account policy or interaction sources. The current `playerVoted` lists cannot supply reliable unique UUID counts (`main.java:93-94,369-372`).
11. **Trade warnings and partner contracts.** Design §11/§13 calls for optional trade/marketplace and claims/CoreProtect context (`docs/reference/playerstatus-sistema-reputacion.md:246-272,304-317`), but identifies no particular trade or protection plugin/API. Decide which integrations are required for the first release, how a trade is confirmed, and whether warnings can ever block a transaction. The design says basic play must continue.
12. **Vouch guarantee economics.** Design §12 leaves stake minimum, duration, objectively severe negative events, loss amount, expiration and withdrawal/rollback rules open (`docs/reference/playerstatus-sistema-reputacion.md:274-302`). The owner's fixed honor charge does not define vouch stake pricing. No current implementation exists (`Commands.java:21-125`).
13. **Public comments, moderation and privacy.** Design §9 requires a negative reason and Bobba replacement, but leaves word list/pattern policy, language scope, moderation permissions, retention, public actor visibility and edit/reversal rules open (`docs/reference/playerstatus-sistema-reputacion.md:208-230,397-400`). Current vote command collects none of it (`Commands.java:94-105`).
14. **GUI confirmation versus command fast path.** Design §8 requires exact-price preview, comment and final confirmation (`docs/reference/playerstatus-sistema-reputacion.md:172-206`), but the baseline command immediately mutates score (`Commands.java:94-104`; `main.java:104-145`). Decide whether commands must open the same confirmation flow and how a changed balance/cost or disconnected target invalidates a pending action.
15. **Release order versus new scope.** Design §16 places GUI, Confidence, Vouching and integrations in later phases (`docs/reference/playerstatus-sistema-reputacion.md:374-384`); owner adds duels and low-status effects now. Clarify release priority and whether the duel system is native to PlayerStatus or an external integration. The target platform itself is already decided.

No removals or relocations of the specific Bukkit calls used by this baseline were confirmed from the available Paper documentation. The demonstrable 26.3 blockers are the startup/config mismatch and the untargeted build; the remaining items above are behavioral failures or design risks, not asserted binary incompatibilities.
